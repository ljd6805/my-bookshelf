지식이 다음 질문으로 이어지는 서재

32권의 구조와 대표 학습 경험을 살펴보고, 나만의 교과서 시리즈를 위한 집필·시각화·운영 기준을 도출했다.

대상: 책을 만들고 연결할 저자 · Codex · Claude   |   관찰과 제안을 구분하여 작성

01

가져올 것은 디자인보다 학습의 연결 방식이다

이 서재의 강점은 많은 책을 한 화면에 진열한 데서 끝나지 않는다. 독자가 가진 질문을 책으로 연결하고, 책의 큰 흐름을 장으로 나누며, 장 안에서는 입력을 바꾸어 결과를 확인하게 한다. 마지막에는 배운 원리를 새로운 문제에 적용하게 한다.

따라서 우리 서재의 출발점은 “무슨 책을 만들까?”와 함께 “독자가 끝나고 무엇을 설명하거나 판단할 수 있어야 할까?”를 정하는 것이다. 화면 스타일은 그 학습 흐름을 지원하도록 선택한다.

관찰한 핵심

질문 중심의 진입, 장 사이의 인과 관계, 반복해서 사용하는 사례, 계산 결과와 그림의 동시 갱신, 종합 문제로의 회수가 서로 맞물린다.

우리의 적용 방향

서재는 책과 학습 경로를 연결한다. 개별 책은 하나의 중심 질문과 사례를 책임진다. 각 실험은 독자가 확인할 변화와 설명할 결론을 갖는다.

판단의 범위: 이 보고서는 웹 구조와 학습 설계를 분석한 것이다. 실제 학습자 비교 실험을 하지 않았으므로 이해도 향상이나 학습 효과를 입증했다고 주장하지 않는다.
02

무엇을 확인했고, 어디까지 검증했는가

32출간된 책의 첫 화면·목차 직접 열기

확인 층위실제 수행이 결과가 의미하지 않는 것
브라우저 관찰포털 14개 경로, 32권의 첫 화면과 목차를 열었다. 읽기 경로를 펼치고 책·본문 링크를 클릭했다. 대표 실험의 입력과 결과를 비교했다.594개 본문 전부를 화면으로 정독하거나 3,903개 실험을 모두 조작한 것은 아니다.
정적 전수 검사카탈로그, 실제 링크, 브라우저 목차, 실험 목록에서 발견한 648개 URL을 읽었다. 644개가 응답했고 4개는 404였다. 성공한 본문은 594개다.648은 고유한 학습 장 수가 아니다. 홈·포털·실험 전용 페이지·index 별칭을 포함한다.
실험 앵커 검사실험 목록 3,903개가 가리키는 페이지와 HTML id를 대조했다. 등록 앵커의 누락은 0개였다.id가 있다는 사실은 계산 정확성·화면 표시·조작 성공을 보장하지 않는다.

03

한 서재 안에 세 가지 진입 경로가 있다

독자는 분야를 이미 알고 있을 수도 있고, 질문만 있을 수도 있으며, 재미있는 실험 하나에 끌릴 수도 있다. 원본은 이 세 상태에 각각 입구를 제공한다. 모두가 첫 장부터 읽어야 한다고 가정하지 않는 설계다.

중요한 차이는 분류와 순서를 분리한 점이다. 분야 지도는 지식이 어디에 속하는지 보여 주고, 읽기 경로는 지금 독자가 어떤 순서로 무엇을 배워야 하는지 설명한다. 분야 이름만 나열해서는 학습 순서가 생기지 않는다.

04

포털의 각 페이지는 어떤 역할을 맡는가

페이지실제 연결과 역할우리 서재의 적용
홈32권 책등, 일/생활의 두 갈래, 질문형 실험 카드, 저자의 공부 동기에서 각각 책·분야·실험으로 진입한다.독자가 바로 시작할 수 있는 대표 질문 3개와 책장을 우선 배치한다.
전체 책장총 39권 중 출간 32권을 기본 노출한다. 주제 검색, 갈래·분야·집필 상태 필터가 있다.완성된 책과 구상 중인 책을 구분한다. 필터는 책 수가 늘어날 때 추가한다.
읽기 길잡이20개 책 간 경로와 3개 짧은 실험 경로. 시작 독자·볼 주제·이동 이유·남길 기록·최종 질문을 제공한다.책을 연결할 때 이동 이유와 완료 결과를 함께 기록한다. 처음에는 경로 1개면 충분하다.
실험 찾기검색·분야/책/난이도 필터·페이지 나눔으로 3,903개 실험의 본문 앵커로 이동한다. “청킹” 입력 시 2개 결과가 나왔다.실험은 별도 복제 페이지보다 본문의 안정적인 id로 연결한다.
반도체기초 물리→설계→제조→패키징·테스트→제품→산업의 여섯 구역으로 지식 지도를 만든다.업무 공정과 선수 개념을 한 종류의 화살표로 혼동하지 않는다.
컴퓨터·SW컴퓨터의 기초와 연결·운영을 나누고, 출간 책과 예정 책을 함께 보여 준다.기초와 운영 수준을 구분한다.
AI·데이터수학·데이터와 학습·모델의 두 층을 제시한다.AI 응용을 소개할 때 필요한 수학·평가 기초를 찾아갈 경로를 둔다.
기기·시스템회로, 빛과 색, 완성 기기와 이동 수단으로 묶는다.부품의 원리를 완제품의 제약과 연결한다.
돈·금융돈·주식·보험 책을 생활의 선택이라는 맥락으로 모은다.분류의 이름을 전문 용어보다 독자의 목적에 가깝게 쓴다.
집·부동산아직 출간된 책이 없는 분야에 예정 범위와 실험 아이디어를 표시한다.빈 분야에 작동하지 않는 읽기 버튼을 만들지 않는다.
건강몸의 여러 계통을 통합하는 한 권으로 연결한다.책 수가 적어도 학습 목적을 한 문장으로 설명한다.
취미·교양카메라·음악·수학을 직접 조작하는 경험으로 묶는다.관심 주제에서 공학 원리로 진입할 기회를 만든다.
로드맵출간·집필 중·예정을 구분한다. 확인 시점에는 32/39권, 집필 중 0권, 예정 7권이었다.아이디어 수를 완성률에 섞지 않는다.
독자 의견책·유형·공개 범위를 선택하는 제보 폼이 있고, 책의 제보 링크에는 책과 페이지 정보가 붙는다. 폼을 열기만 했으며 전송하지 않았다.초기에는 문맥이 담긴 GitHub Issue 링크로 충분하다. 별도 의견 서버는 나중에 판단한다.
독자에게는 진입 경로를 제공하고, 저자에게는 단일한 목록을 제공한다. 원본의 books.json, paths.json, discovery.json 분리는 이 둘을 함께 다루는 구조다.
05

32권에서 반복되는 여섯 가지 이야기 방식

방식관찰 사례학습을 이어 주는 장치적용할 때 주의할 점
하나의 대상이 변한다SensorBook: 광자→전하→픽셀→읽기→영상. DisplayBook은 전기 신호가 빛으로 나오는 반대 방향을 다룬다.앞 장의 출력이 다음 장의 입력이 된다. 독자가 같은 대상을 계속 추적한다.단계를 바꿀 때 보존되는 값과 새로 생기는 손실을 명시한다.
같은 제품을 완성한다AnalogBook의 AB-1 센서 인터페이스 칩, SoCBook의 SB-1.장마다 부품을 배우고 공통 사양에 다시 연결한다.실험마다 데이터가 달라지면 동일 제품의 연속 결과라고 오해하지 않도록 알린다.
하나의 사건을 조사한다YieldBook의 YB-12, FailureBook의 이어지는 사건과 최종 수사실.관찰→가설→검사→증거→판단으로 지식의 사용 순서를 만든다.모양만 보고 원인을 외우게 만들지 않는다. 반례와 추가 증거를 둔다.
한 사람의 선택이 쌓인다MoneyBook의 한결, StockBook의 투자 노트, InsureBook의 지우네, BodyBook의 다온.각 장의 선택을 장기 결과와 연결하여 읽을 동기를 유지한다.교육용 인물과 가정값을 실제 개인의 예측처럼 제시하지 않는다.
익숙한 결과에서 원리로 거슬러 간다CameraBook의 사진·오해, PhoneBook의 분해, MathBook의 실제 물건과 문제.독자가 이미 아는 결과에서 “왜?”를 만들어 추상 개념으로 진입한다.비유를 한 번 쓴 뒤 실제 변수와 정확한 정의로 돌아온다.
배운 도구를 새 문제에 쓴다DesignBook 도전 과제, AI 서빙 설계, 센서·SoC·공정 실험실.개별 장의 지식을 비용·성능·제약 안에서 선택하는 종합 문제로 회수한다.화려한 종합 대시보드만 만들고 무엇을 결정할지 빠뜨리지 않는다.

해석: “스토리텔링”은 등장인물이나 비유를 억지로 늘리는 일이 아니다. 같은 질문과 대상이 장을 지나며 어떻게 달라지는지 보여 주는 일이다. 기술 교과서에는 특히 ‘변환 과정’, ‘설계 사양’, ‘문제 해결’이 잘 맞는다.

06

사례 1 · 광자에서 사진까지, 장을 잇는 방법

SensorBook 첫 장은 센서의 출발점을 광자 수로 잡는다. 다음 장의 도입은 그 광자가 실리콘 안에서 전하로 바뀌는 과정으로 이어진다. 실제로 ‘다음 장’을 눌러 광전 변환과 픽셀 구조까지 이동했다. 후반의 연결은 전체 본문 목차와 링크 구조를 대조했다.

단계그 장이 해결하는 질문다음 장이 필요한 이유
빛과 광자픽셀에 어떤 빛이 얼마나 들어오는가?빛이 들어와도 전기 신호가 생기는 방식은 아직 모른다.
광전 변환빛을 전자로 바꾸고 모으는 것은 무엇인가?그 기능을 작은 픽셀 안에 배치하는 구조가 필요하다.
픽셀 구조렌즈·필터·포토다이오드·배선은 어떻게 쌓이는가?모인 전하를 읽고 숫자로 바꾸어야 한다.
읽기·노이즈·특성읽힌 값은 왜 흔들리고, 무엇으로 성능을 평가하는가?불완전한 측정값을 쓸 만한 영상으로 만드는 과정이 필요하다.
셔터·ISP·계산 사진측정 방식과 신호 처리가 영상에 어떤 차이를 만드는가?사용 환경에 맞는 센서 사양을 선택해야 한다.
최종 설계픽셀 크기·노이즈·대역폭 등 제약을 함께 만족하는가?앞 장의 변수들을 다시 꺼내 하나의 선택으로 종합한다.
직접 확인한 실험: 파장 550 nm일 때 표시 에너지는 2.254 eV, 흡수 표시는 ‘흡수 가능’이었다. 1,200 nm 버튼을 누르자 1.033 eV와 ‘투과’로 바뀌었다. 에너지 막대, 파장 위치, 수치와 설명이 같은 입력에 반응했다. 이 수치는 화면 관찰값이며 전체 광학 모델 검증을 뜻하지 않는다.

우리의 규칙: 각 장의 첫 문장에 “앞 장에서 얻은 것”을, 마지막 문장에 “아직 해결하지 못한 것”을 적는다. 다음 장 링크에는 번호와 제목뿐 아니라 이동 이유를 붙인다.

파장 실험 화면빛과 광자 원문광전 변환 원문픽셀 구조 원문

사례 2 · 실패를 나누어 보게 하는 RAG 실험

AIBook의 RAG 장은 같은 가상 문서함을 청킹, 검색, 순위 결합, 프롬프트 조립, 평가에 반복해서 사용한다. 독자는 알고리즘 이름을 외우기 전에 “원문에 답이 있는데 왜 못 찾았는가?”를 관찰한다.

서재의 짧은 경로는 이 장을 그대로 요약하지 않는다. 의미 공간 이해→청킹 경계 확인→검색 순위 비교→평가의 네 단계에 각각 해야 할 일과 남길 기록을 붙이고, 끝에서 조사 순서를 설명하게 한다.

직접 조작관찰 결과배울 수 있는 구분
고정 길이 120자 → 문장 분할기본 상태는 4개 청크와 잘린 문장 3/10. 문장 분할 후 5개 청크, 잘린 문장 0/10으로 바뀌었다.검색 알고리즘을 바꾸기 전에 자료가 잘리지 않았는지 볼 수 있다.

장말 퀴즈의 RAG 선택지 클릭정답의 이유와 다른 접근의 한계를 설명하는 피드백이 나타났다.정답 표시를 이해의 종착점으로 삼지 않는다.
중요한 모델 구분: 원문은 검색 실험의 벡터가 신경망 임베딩이 아니라 문자 n-gram TF-IDF라고 설명한다. 에이전트의 판단 부분도 대본 규칙임을 표시한다. “실제 계산”과 “실제 LLM”을 같은 말로 쓰지 않는 태도를 가져와야 한다.

우리의 규칙: 같은 사례를 여러 실험에서 사용할 때에는 입력 자료를 공유한다. 독립된 자료라면 “같은 사건의 연속 데이터가 아니다”라고 적는다. 실험 아래에는 반드시 ‘모형에서 실제로 계산하는 것’과 ‘생략하거나 대신한 것’을 표시한다.

표현원본에서 확인한 사용어떤 질문에 적합한가우리의 구현 기준
SVG 구조도RAG의 색인·질의 흐름, 픽셀 단면, 개념·연결 도해. 소스의 SVG 요소를 확인했다.무엇이 어디에 연결되고 어떤 순서로 작동하는가?정확한 라벨과 화살표를 우선한다. 짧은 대체 설명도 함께 제공한다.

화면 문법의 장점: 큰 그림 옆에 조작부를 두고, 그 아래 수치와 해석을 배치한다. 장 안의 목차와 상단의 책 검색이 현재 위치를 보완한다. 밝은 배경, 제한된 강조색, 본문과 실험 영역의 경계가 긴 페이지에서도 구조를 드러낸다.

따라 하면 안 되는 것: 모든 개념에 3D나 애니메이션을 붙이는 것. 무엇이 변하는지 알 수 없는 움직임, 단위 없는 수치, 원인과 무관한 효과는 학습을 방해한다. 휴대전화·키보드·화면 읽기 프로그램에서는 별도 점검이 필요하다. 이번 화면 관찰은 데스크톱 브라우저 기준이다.

실험 하나를 완성하는 여덟 가지 조건

1. 질문과 예측무엇을 확인할지, 움직이기 전에 어떤 결과를 예상하는지 묻는다.
2. 입력과 범위변수·단위·기본값·범위·고정 조건을 보인다.
3. 계산과 가정같은 입력으로 수치와 그림을 계산한다. 단순화와 근거를 명시한다.
4. 변화와 비교한 변수만 바꾼 전후를 즉시 구분할 수 있게 한다.
5. 결과 해석왜 달라졌는지 짧은 문장과 값으로 설명한다.
6. 초기화와 재현초기화·프리셋·시드 또는 사건 번호로 다시 비교한다.

7. 접근 가능한 대안: 드래그만 강요하지 않고 버튼·숫자 입력·키보드를 제공한다. Canvas나 WebGL이 실패해도 질문과 핵심 결과를 읽을 수 있어야 한다.

8. 이해 확인: 새 조건에서 결과를 예측하거나 다른 사람에게 설명하게 한다. “슬라이더가 움직인다”는 UI 검사와 “모델이 맞는다”는 계산 검사를 별도로 통과해야 한다.

판정 수준통과 증거
L1 · 접근페이지·스크립트·앵커가 열리고 핵심 설명이 보인다.
L2 · 반응입력 변경 전후에 관련 수치와 그림이 함께 바뀐다.
L3 · 모형기준값, 극단값, 보존 관계, 재현 가능한 샘플을 독립 계산과 비교했다.
L4 · 학습대표 독자가 새 조건의 결과와 이유를 설명할 수 있다. 정식 학습 효과 주장은 별도 실험이 필요하다.
실험을 출간할 때 L1~L3의 확인 범위를 기록한다. L4는 소수 독자 시연부터 시작한다. “클릭해 봤다”를 “계산 검증 완료”로 바꾸어 적지 않는다.

비판적으로 가져와야 할 운영 교훈

1. 책이 늘면 가장 먼저 연결과 메타데이터가 낡는다

관찰 근거확인한 문제운영 기준
카탈로그 ComputerBook 15장 / 실제 발견 본문 23개책장 카드의 장 수가 본문 확장과 함께 갱신되지 않았다.장 수는 선언 목록이나 빌드 결과에서 계산한다.
카탈로그 DesignBook 14장 / 실제 발견 본문 16개실험실·도전 과제 등을 포함한 실제 파일 구성과 목록 수가 달랐다.“장”에 포함하는 범위를 정의하고 같은 정의로 집계한다.
카탈로그 실험 수 합 3,857 / 검색 목록 3,903카드의 숫자는 +가 붙는 소개 수치라 정확한 전수 목록과 동일하지 않다.개요 수치와 실제 검색 건수를 구분하고 기준일을 붙인다.

2. 책 간 본문 링크 4개가 404를 반환했다

출발 페이지연결된 주소의 문제
ChipIndustryBook / equipmentLithoBook의 /euv.html로 연결. 실제 발견한 본문 경로는 /chapters/euv.html이다.

YieldBook / signatureProcessBook의 /chapters/etching.html로 연결. 발견한 식각 본문은 /chapters/etch.html이다.

이 목록은 검사 시점의 HTTP 응답에 근거한다. 원본 사이트를 수정하지 않았다. 정상 경로를 찾았다고 해서 내용상 가장 적합한 대체 링크까지 모두 확정한 것은 아니다.

3. 큰 그림이 그려지지 않아도 설명은 남아야 한다

센서 픽셀 3D의 분해도 값은 변경되었지만 그림 영역은 비어 있었다. 콘솔에는 WebGL context를 생성하지 못했다는 오류와 GPU 렌더러 비활성 상태가 기록되었다. 이는 이번 점검 환경의 한계이며, 사용자 환경에서도 동일하다고 단정할 수 없다. 다만 대체 단면도가 없으면 독자는 빈 영역 앞에서 막힌다.

4. 많은 실험과 긴 본문은 선택 부담을 만든다

RAG처럼 한 장 안에 학습 목표와 실험이 많은 구성은 참고서로 유용하지만, 초심자에게는 한 번에 해야 할 일이 많다. 우리 책은 ‘오늘 꼭 해 볼 실험 1개’, ‘더 깊이 보기’를 구분한다. 처음부터 32권의 규모를 따라갈 필요는 없다.

5. 최신 기술 설명에는 검토 날짜가 필요하다

원본의 최신 모델·가격·제품 수치는 이번 보고서의 사실 근거로 재사용하지 않았다. 우리 책에서도 원리 설명과 시점 의존 정보를 분리하고 후자에는 원문 출처와 마지막 검토일을 붙인다.

12

서재 하나, 책 저장소 여러 개로 운영한다

권장 구조: my-bookshelf는 책 목록, 읽기 경로, 공통 집필 기준과 프로젝트 문서를 관리한다. 각 교과서는 독립 저장소에서 본문·실험·출처·검증을 관리하고 자기 GitHub Pages로 배포한다. 독자는 링크로 오가며, 에이전트는 Git 기록과 공통 지침을 따라 작업한다.

위치책임초기에 넣지 않을 것
서재 저장소카탈로그, 교차 학습 경로, 운영 기준, 분석 보고서, 문서 허브.모든 책의 복제 코드, 계정 서버, 통합 LMS.
책 저장소장별 본문, 실험 모델, 자산, 출처, 단위 테스트, 출판 상태.다른 책의 내부 파일에 대한 빌드 의존.
연결 규약책 id·장 id·실험 id, 실제 site URL, 선수 내용, 다음 이동 이유.브라우저가 매번 모든 저장소를 읽어 합치는 구조.

GitHub Pages에서 반드시 달라지는 점

원본은 책마다 다른 하위 도메인을 쓴다. 같은 계정의 GitHub 프로젝트 Pages는 일반적으로 https://사용자.github.io/저장소/ 아래에 위치한다. 따라서 책 내부 자산에 /assets/...처럼 호스트 루트를 가정하면 저장소 경로를 벗어날 수 있다. 내부 링크는 상대 경로나 설정된 base path를 쓰고, 책 간 링크는 카탈로그에 기록한 완전한 URL을 쓴다.

또한 같은 계정의 프로젝트 Pages는 보통 같은 origin을 공유한다. localStorage도 origin 단위이므로 progress 같은 범용 키는 책끼리 충돌할 수 있다. bookshelf:book-id:v1:progress처럼 이름을 구분한다. 브라우저에 저장된 기록은 계정 동기화나 영구 보관이 아니라는 점도 독자에게 알린다.

연결은 글의 일부로 관리한다

교차 링크 한 건에는 출발 장, 도착 장, 이동 이유, 필요한 배경, 돌아올 위치를 기록한다. 처음에는 JSON 파일 한 개면 된다. 변경이 잦아진 뒤에만 자동 수집과 릴리스 동기화를 검토한다. Git submodule이나 공통 npm 패키지를 먼저 도입할 이유는 아직 없다.

기술 근거: GitHub Pages 공식 설명, 프로젝트 사이트 경로, localStorage의 origin 범위. 위 저장소 분리는 이번 분석의 설계 제안이다.

13

Codex와 Claude가 같은 결정을 이어받게 한다

공동 작업의 기준은 특정 모델의 기억이 아니라 저장소의 현재 문서다. AGENTS.md를 공통 지침으로 두고 CLAUDE.md에서는 같은 파일을 참조하게 한다. 기준을 두 군데에 복사하면 언젠가 서로 다른 지시가 된다.

공유해야 하는 것기록 위치작업 규칙
목적과 독자기획 HTML, 책 기획 템플릿코드 작성 전에 이번 장의 질문·완료 결과·모형 범위를 적는다.
확정 결정운영 기준 HTML, 결정 표아이디어·권장안·확정안을 구분한다.
작업 범위작업 상태 JSON, 인수인계 HTML담당 파일과 검증 범위를 적는다. 동시에 같은 파일을 편집하지 않는다.
검증 결과검증 HTML과 테스트 결과실행한 검사, 성공·실패, 미확인 항목을 분리한다.
코드 품질AGENTS.md 및 테스트함수는 100줄 이하. 계산과 표시를 분리하고 계산식·경계값·회귀 문제를 테스트한다.

Claude 공식 문서의 import 규칙에 따라 CLAUDE.md에서 @AGENTS.md를 참조한다. 도구 버전과 설정에 따라 로딩 동작이 달라질 수 있으므로 첫 작업에서 실제로 읽힌 지침을 확인한다. 이 파일들은 계정 권한을 부여하거나 Codex와 Claude를 자동 실행시키는 장치가 아니다.

구체적인 시작 순서와 인수인계 양식은 공동 작업 문서에 정리했다. 첫 책을 만들 때에는 책 기획 템플릿부터 채운다.

책 한 권의 한 장으로 운영 기준을 검증한다

순서산출물다음 단계로 넘어갈 조건
1 · 지금이 분석 보고서, 점검 목록, 운영 기준, 공통 지침, 문서 허브.기준 문서가 저장소에 저장되고 다음 작업자가 찾을 수 있다.
2 · 첫 사례책 하나의 중심 질문과 끝까지 따라갈 사례, 장의 인과 관계 지도.각 장이 이전 장의 무엇을 받아 어떤 문제를 해결하는지 설명된다.
3 · 대표 장 하나도입·그림·실험·퀴즈·다음 장 연결이 완결된 작은 장.대표 독자가 입력을 바꾸고 결과의 이유를 설명한다.
4 · 책 확장검증된 형식을 다음 장에 적용. 계산과 시각화는 주제에 맞게 설계.장별 완료 기준과 교차 링크 검사를 통과한다.
5 · 서재 연결실제 배포 URL, 책 설명, 선수 지식, 추천 경로 등록.책→서재→다음 책의 왕복 이동을 확인한다.
첫 시범 사례 제안: “문서에 답이 있는데 AI가 틀리는 이유”처럼 한 가지 실패에서 출발하면, 문서 분할·검색·생성·평가를 하나의 이야기로 묶기 쉽다. 이는 후보이며, 이번 작업에서 새 교과서를 집필하거나 기존 책을 수정하지 않았다.
