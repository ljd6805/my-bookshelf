LLM 시스템 교과서 · 문서 허브

《LLM은 컴퓨터에서 어떻게 실행되는가》의 기획, 구현과 검증을 연결한다. 학습 본문과 운영 문서를 구분한다.

1. 기획

독자·학습 목표·4부 12장·분권 기준

첫 권은 실행 원리와 하드웨어 제약을 이해한다. CUDA 구현과 프로파일링은 후속 심화편 후보로 남긴다.

2. 구현

파일 구성·계산 가정·공식 모델 사례·문제 해결

12장, 14개 실험, 12개 확인 문제와 표지 대표 실험. CPU↔GPU와 GPU 내부 전송, 가중치와 KV, 전체와 활성 파라미터를 구분한다.

3. 검증

계산·브라우저 확인과 검증 한계

L1~L3를 확인하며 L4 실제 학습 효과와 실물 GPU 성능은 검증 범위에 포함하지 않는다.

4. 2026-10-12 보충

  • 공통: 12개 장마다 전이 문항(transfer, “다른 상황에 써 보기”)을 확인 문제 블록 안에 더했습니다. 블록을 새로 만들지 않아 일곱 블록 순서는 그대로입니다. 보기 순서는 화면에서만 돌려(choiceOrder) 확인 문제의 정답은 장 순번 % 3번째 자리, 전이 문항의 정답은 그다음 자리에 오고, 데이터의 정답 번호와 data-answer·data-transfer 값은 원래 번호를 유지합니다. 장 머리의 문구는 “확인 문제 2개”가 됩니다.
  • 공통 사례 숫자로 잇기: 1장에서 회의록 입력 3,000토큰·요약 출력 300토큰(가상 Dense 8B, 16bit)을 정하고, 2~12장 둘째 문단에 그 장의 도구로 계산한 한 문장씩을 더했습니다. 선형층 16,781,312개, 14.90 GiB·3.73 GiB, 토큰 ID 약 12 KB, decode 299회 × 16 GB ≈ 4.8 TB 읽기, prefill 투영 약 1,007억 FLOP 대 decode 약 3,355만 FLOP, 투영 위치 3,299 대 944,850, KV 3,300 × 128 KiB ≈ 412.5 MiB(10명 4.03 GiB), 500 GB/s에서 단계 하한 32 ms·약 9.6초, 4bit 8 ms·약 2.4초, Qwen3-8B 464.1 MiB·Qwen3-30B-A3B 309.4 MiB, 12장 예산 22.39 GiB입니다. 12장 실험의 셋째 예제를 “회의 요약 8명”(16bit, 4,096토큰 × 8)으로 바꿨습니다. 실험 수는 14개 그대로입니다.
  • 검산: 위 숫자와 전이 문항 값(100,761,600개, 6.52 GiB, 549위치·26,225위치, 1.6875 GiB, 2 ms, 40 GB, 2.5 GiB 대 26.08 GiB, 12.10 GiB)을 GMath와 따로 계산해 맞췄습니다.
  • 검증: npm test, python3 scripts/validate.py(0 오류), python3 scripts/build_catalog.py --check(통과), tests/browser.cjs(1280·390·320px에서 모든 장의 확인 문제·전이 문항 정답/오답 클릭, 실험 예제·경계값·초기화, 가로 넘침, 서가로 버튼)를 실행해 모두 통과했습니다.
  • 확인하지 못한 것: 전이 문항이 실제로 새 상황 적용을 돕는지(L4 학습 효과)는 독자로 확인하지 않았습니다. 집필자가 자기 글을 검수하지 않으므로, 이번 보충은 다른 세션의 팩트·출처 검수 새 회차가 필요합니다. 토큰 ID를 4 byte 정수로 보낸다는 것은 가정이며 엔진마다 다릅니다.

5. 2026-10-12 2차 보충

  • 9장 #bottleneck roofline 실험(검토서 제안 2): 단계 종류(decode/prefill), prefill 입력 토큰 수 T(1·10·100·300·1,000·3,000), 가중치 bit 선택을 더했습니다. 한 단계의 위치 수 N은 decode에서 B, prefill에서 B × T이고(GMath.stepTokens), 결과에 이 장비의 기준점(연산 ÷ 대역폭, 기본 100 FLOP/byte)을 함께 보입니다. 대표값: 16bit 8B, 500 GB/s·50 TFLOP/s에서 T = 1이면 32 ms(메모리 제한), T = 100이면 두 하한 모두 32 ms·집약도 100, T = 3,000이면 계산 하한 960 ms(연산 제한). 기본값은 decode·4bit라 기존 결과(8 ms)는 그대로입니다. 예제 “회의록 prefill · 16bit”를 더했고 본문 둘째 문단과 formulaNote에 prefill 계산과 Attention T² 생략을 적었습니다.
  • 3장 #weights 가중치 실험(제안 3): “묶음 눈금”(없음·32·64·128개마다 16bit scale)과 “영점 함께 저장”을 더했습니다(GMath.effectiveBits). 대표값: 8B·4bit에서 묶음 32 → 4.5bit·4.5 GB, 64 → 4.25 GB, 128 → 4.125 GB, 128+영점 → 4.25 GB. 깊이 읽기에 셋째 문단을 더해 12장 “가중치 부가정보” 비율과 잇습니다(4.5bit → 12.5%). 특정 파일 형식(GGUF·GPTQ·AWQ)의 묶음 크기는 인용하지 않고 교육용 가정으로 표시했습니다.
  • 시리즈 연결: 3장 “더 읽어 보기”에 추론 최적화편 7장 #evidence로 가는 링크를 더했습니다. 그 장에 새로 쓴 “양자화를 속도 수단으로 볼 때”가 이 장의 묶음 눈금 계산(4.125bit)을 decode 하한으로 이어 갑니다.
  • 새 실험 ID는 없습니다(실험 14개 유지). 두 계산은 tests/math.test.cjs에 대표값으로 고정했습니다.
  • 건너뛴 것: 제안 4(11장 전이 문항)는 1차 보충의 장마다 전이 문항으로 이미 채워졌습니다.
  • 문체 비평 메모(다온): ① 3장 “4bit 정수만으로는 원래 크기를 알 수 없으므로” — “크기”가 파일 크기로도 읽힙니다. → “원래 값이 얼마나 컸는지 알 수 없으므로”. ② 9장 “T가 같은 자리에 들어가는 것을 볼 수 있습니다” — “~하는 것을 볼 수 있습니다”는 번역투이고 독자에게 할 일을 흐립니다. → “실험에서 단계 종류를 prefill로 바꾸면 배치 B가 있던 자리에 입력 길이 T가 들어갑니다.” ③ 3장 “첫 실험의 “묶음 눈금” 선택이 이 계산을 합니다.” — 선택 상자가 계산하는 주어가 되어 어색하고, 독자가 할 일이 빠졌습니다. → “첫 실험에서 “묶음 눈금”을 고르면 이 값을 계산해 보여 줍니다.”
  • 확인하지 못한 것: 학습 효과(L4). 실제 장비 실측은 하지 않았습니다. 다른 세션의 팩트·출처 검수 새 회차가 필요합니다.
