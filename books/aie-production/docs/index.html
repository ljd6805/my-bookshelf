AI 인프라와 운영 · 제작 문서

「AI 엔지니어링 처음부터」 시리즈 18권 《AI 인프라와 운영 · 모델 서버에서 운영 장부까지》의 기획, 원본 레슨 대응, 구현, 검증을 한곳에 모았습니다. 작성일 2026-10-08. 원본은 rohitg00/ai-engineering-from-scratch(MIT)의 Phase 17 · Infrastructure and Production입니다. 원문과 코드를 옮기지 않았고, 개념과 순서만 참고해 새로 썼습니다.

1. 기획

  • 독자: LLM을 API로 불러 본 적은 있지만, 직접 모델 서버를 올리고 비용과 지연, 사고를 책임져 본 적은 없는 엔지니어. vLLM, goodput, 카나리라는 이름은 알아도 “지금 우리 서비스에 어느 손잡이를 돌려야 하는지” 숫자로 말하기 어려워합니다.
  • 끝의 행동: 운영 보고 하나를 받고, 원인을 어느 장의 변수(웜 풀, 프롬프트 순서, 청크 프리필, 라우팅)에서 찾을지 고른 뒤, 같은 계산을 다시 돌려 처방이 실패한 지표를 실제로 움직이는지 확인합니다.
  • 공통 사례: 다온의 상담 챗봇 누리봇. 쇼핑몰·병원 예약·유럽 매장 세 고객사가 하루 약 5만 건을 보내고, 요청마다 공통 접두부 2,000토큰·고객별 내용 500토큰·답 200토큰을 씁니다. 70B 모델을 H100 80GB에 올리고, 목표는 TTFT 800ms·TPOT 25ms·전체 3,000ms입니다.
  • 이야기 방식: 하나의 제품을 완성한다. 장마다 누리봇 운영에 필요한 결정 하나(어디서 돌릴지, 어떤 형식으로 담을지, 엔진을 어떻게 설정할지, 무엇을 잴지, 어떻게 빠르게 할지, 어디로 보낼지, 언제 늘릴지, 청구서를 어떻게 줄일지, 무엇을 지킬지, 어떻게 바꿀지, 사고에 어떻게 대비할지)를 계산으로 내리고, 마지막 장에서 월요일 아침의 운영 보고 세 가지를 진단합니다.
  • 범위: 원본 Phase 17의 레슨 28개 전부. 페이지 KV, 연속 배치, 지표 정의, 가중치 형식처럼 서재의 LLM 시스템(books/llm-gpu)·LLM 성능(books/llm-performance) 책이 깊게 다룬 내용은 한 문단으로 줄이고 그 장으로 링크합니다. 대신 운영 결정과 비용, 확률로 따지는 배포·사고 대응에 분량을 씁니다.
  • 증거: 실험 16개는 모두 브라우저에서 js/math.js의 함수로 계산합니다. 실제 계산인지, 시드를 고정한 시나리오인지, 교육용 가정값이 무엇인지를 결과 문장마다 밝힙니다. 가격·제품 상태·버전은 원본 커리큘럼 기준(확인일 2026-10-08)으로만 쓰고 현재 가격표로 제시하지 않습니다.

2. 원본 레슨 대응표

레슨 28개가 모두 한 장 이상에 들어갔습니다. 각 장의 “더 읽어 보기”에 원본 레슨 폴더 링크를 출처로 두었습니다.

01Managed LLM Platformsplatform세 갈래 플랫폼이 값을 매기는 단위만 요약하고, 토큰과 GPU의 손익분기 계산(breakeven)으로 옮겼습니다.
02Inference Platform Economicsplatform플랫폼별 가격 단위와 지속 사용률이 갈림길이라는 판단을 손익분기 실험의 중심으로 삼았습니다.

04Serving Engine Internalsengine페이지 KV와 연속 배치는 LLM 성능 책으로 보내고, 청크 프리필의 맞바꿈(chunk)을 계산합니다.
05EAGLE-3 Speculative Decodingspeculative수락률 α와 기대 토큰 수의 정확한 식, 부하에 따른 손익분기(spec)를 계산합니다.
06Prefix-Cache Serving · RadixAttentionlocality접두부 트리와 캐시를 아는 라우팅을 라우팅 시뮬레이션(router)으로 확인합니다.
07FP8 and NVFP4 on BlackwellprecisionFP8·NVFP4의 바이트 수와 배율 값이 HBM 예산(hbm)에 미치는 영향만 다룹니다.
08Inference Metrics · TTFT, TPOT, ITL, Goodputmetrics, final네 지표와 도구마다 다른 ITL 정의, goodput을 합성 분포 실험(goodput)으로 계산합니다.
09Production QuantizationprecisionAWQ·GPTQ·FP8 가중치 형식과 KV 형식을 따로 고르는 판단을 HBM 예산 실험에 넣었습니다.
10Cold Start Mitigationscaling, final원본의 70B 단계별 시간 표를 바탕으로 완화책과 웜 풀 비용(coldstart)을 계산합니다.
11Multi-Region Serving and KV Localitylocality리전 사이 라우팅과 데이터 거주 요구를 KV 위치의 문제로 설명했습니다.
12Edge Inferenceprecision대역폭이 정하는 디코드 상한(edge)으로 기기 위 추론의 한계를 계산합니다.
13LLM Observability Stack Selectionincident추적 기록의 표본 추출 규칙(sampling)과 관측 도구를 고르는 기준을 다룹니다.
14Prompt and Semantic Cachingcost, final접두부 캐시의 읽기·쓰기 단가와 순서의 중요성을 청구서 실험(bill)으로 계산합니다. 의미 캐시의 위험도 설명합니다.
15Batch APIscost배치 할인과 캐시를 겹치는 계산을 청구서 실험의 처리 차선으로 넣었습니다.
16Model Routingcost값싼 모델 먼저 보내기와 확신도 검사를 계단식 라우팅 실험(cascade)으로 계산합니다.
17Disaggregated Prefill/Decodespeculative프리필과 디코드 풀 사이 KV 전송 시간(kvtransfer)과 짧은 프롬프트 규칙을 계산합니다.
18Production Serving Stack · KV OffloadingengineKV를 CPU·디스크로 내리는 계층 저장과 운영 스택 구성을 엔진 장에 요약했습니다.
19AI Gatewaysgateway재시도와 대체 공급자(fallback)를 계산하고, 키·한도·기록을 한곳에 모으는 이유를 설명합니다.
20Shadow, Canary, Progressive Deploymentrollout섀도·카나리·점진 배포 단계와 관문이 울릴 확률(canary)을 계산합니다.
21A/B Testing LLM Featuresrollout표본 크기와 여러 번 들여다보기의 위험을 카나리 장에서 확률 책으로 이어 설명합니다.
22Load Testing LLM APIsmetrics부하 시험이 평균이 아니라 분포와 goodput을 봐야 하는 이유를 지표 장에 넣었습니다.
23SRE for AIincidentSLO와 오류 예산, 소진 속도(burnrate)를 계산합니다.
24Chaos Engineering for LLM Productionincident영향 범위와 중단 규칙을 소진 속도 실험으로 연결했습니다. 도구의 재단 지위 같은 바뀌기 쉬운 사실은 쓰지 않았습니다.
25Security · Secrets, Rotation, Audit, Guardrailsgateway비밀 저장, 짧게 사는 자격 증명, 감사 기록을 게이트웨이 장의 지킬 것으로 묶었습니다.
26Compliance Frameworksgateway데이터 거주와 감사 요구가 게이트웨이와 리전 설계에 주는 제약만 요약했습니다. 법적 시행일은 쓰지 않았습니다.
27FinOps for LLMscost요청·고객사별 비용 태깅과 단위 경제를 청구서 장에 넣었습니다.
28Self-Hosted Serving Selectionengine, final하드웨어·규모·작업 순서로 엔진을 고르는 판단을 엔진 장에 요약했습니다. 제품 버전과 유지 보수 상태는 원본 기준으로만 언급합니다.

3. 구현

  • 파일 구조: js/math.js(계산만, DOM 없음) · js/content.js(장 글·출처·실험 설명) · js/labs-serve.js(1~6장 실험) · js/labs-ops.js(7~12장 실험) · js/figures.js(장마다 움직이는 그림) · js/home-lab.js(표지 실험) · js/lab-guides.js(예제와 결과 읽기).
  • 전역 접두어 A18, 서가 삽화 접두어 a18-ill-, 진도 키 bookshelf:aie-18-production:v1:progress.
  • 교육용 가정값: GPU 시간당 4달러, 70B FP8 한 대 처리량 2,300 tok/s(원본 레슨 04의 2,200~2,400 범위), HBM 대역폭 3,350GB/s, 프리필 초당 4만 토큰과 디코드 한 반복 7ms(원본의 “32K 프롬프트 약 800ms”에 맞춤), 링크 속도(원본의 “4K 프롬프트 20~80ms”에 맞춤), API 단가(원본 레슨 15의 예시 단가).
  • 원본의 근사식 가운데 정확하지 않은 것은 고쳐 썼습니다. 추측 디코딩의 기대 토큰은 1 + Kα가 아니라 (1−α^(K+1))/(1−α)를 쓰고, 근사식은 상한이라고 밝혔습니다. 원본 레슨 04·09의 KV 크기 예시처럼 모델 구조와 맞지 않는 수치는 쓰지 않고 Llama 3 70B 구조로 다시 계산했습니다.
  • 난수는 mulberry32에 시드를 고정해 화면과 테스트가 같은 값을 냅니다.

4. 검증

L1 접근(라벨·키보드·상태 알림), L2 반응(입력을 바꾸면 결과가 바뀌고 초기화가 처음 값으로 돌아감), L3 모형(대표값·경계값·불변 조건을 tests/math.test.cjs로 확인), L4 학습(독자가 실제로 이해했는지)으로 나누어 적습니다.
