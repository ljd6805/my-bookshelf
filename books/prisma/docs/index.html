이 문서는 /root/curriculum이라는 실제 별도 실행 세션이 작성했습니다. 한 세션에서 기획·연결팀, 교과과정팀, 교수법팀의 페르소나를 점검 관점으로 적용했습니다. 인물별로 독립 세션이나 회의를 실행했다는 뜻은 아닙니다. 독립 팩트 검수는 이 문서 작성자가 맡지 않습니다.

1. 기획 · G1

독자: 함수·객체·비동기 호출에 익숙하지만 ORM과 데이터베이스 스키마를 함께 설계해 본 경험은 적은 개발자입니다. TypeScript를 처음 접한 독자에게는 타입, Promise, await의 최소 전제를 짧게 설명합니다.

끝의 행동: 독자가 Project·Task·Run을 모델링하고 필요한 조회를 작성하며, 중복 요청과 중간 실패를 시험한 뒤 데이터 변경의 배포 순서를 설명할 수 있게 합니다.

공통 사례: 가상의 AX 작업 이력 저장소입니다. Project에는 여러 Task가 속하고, Task에는 여러 Run이 쌓입니다. 같은 요청을 재시도해도 실행 기록이 중복되지 않아야 하며, 다른 프로젝트의 작업을 수정해서는 안 됩니다. 실제 회사 자료·업무 계정·운영 DB는 사용하지 않습니다.

범위: Prisma ORM 7의 관계형 모델, Client의 생성과 CRUD·관계 조회, Migrate, 트랜잭션·멱등성, 쿼리 관찰, 테스트와 권한 경계까지 한 권에 묶습니다. 설치형 실습의 기본 DB는 SQLite로 두고, PostgreSQL로 옮길 때 재검증할 동시성·인덱스·연결 관리 차이는 구분하여 설명합니다. 설치와 DB 선택의 정확한 예제는 조사 노트와 실행 결과에 맞춰 확정합니다.

학습 증거: 처음 보는 실패 시나리오에서 스키마·조회·변경 순서 중 무엇을 고쳐야 하는지 선택하고, 입력·예상 결과·실제 결과를 적습니다. 마지막 과제는 중복 제출, 중간 실패, 프로젝트 경계 위반이라는 새 조건을 함께 다룹니다.

한 권으로 묶는 이유

스키마만 배운 뒤 운영 문제를 별도 권으로 미루면 데이터 변경과 실패 처리를 놓치기 쉽습니다. 따라서 입문부터 실무 기초까지 10장으로 완결합니다. 고급 DB 튜닝이나 프레임워크별 배포는 확장 주제로 남깁니다. 각 장은 한 문제를 해결하고 다음 문제를 남기므로 메서드 이름을 나열하는 API 사전이 되지 않게 합니다.

서가 자리와 연결 계획

제목은 Prisma · 데이터 모델에서 안전한 변경까지, 책등 제목은 Prisma(6글자), 분류는 컴퓨터, 색은 sage를 제안합니다. 같은 분류의 알고리즘 책 다음에 배치하면 앞 책의 blue와 구분됩니다. 실제 등록 시 양쪽 이웃의 색을 다시 확인합니다.

연결 후보이동 이유반영 범위
알고리즘 책 → Prisma의 성능 장비교 횟수를 줄이는 생각을 실제 DB 조회와 인덱스 선택에 적용합니다.books/algorithms/#index와 books/prisma/#performance 사이 양방향 링크 후보. 역색인·ANN과 관계형 DB 인덱스가 같다는 주장은 하지 않습니다.
AI 인프라와 운영 → Prisma의 트랜잭션 장호출을 재시도할 때 저장 결과가 중복되는 문제를 따로 다룹니다.books/aie-production/의 실제 재시도 장 ID 확인 후 연결합니다. Prisma에서 서비스 전체의 관찰·배포로 돌아가는 이유도 적습니다.
공통 개념·읽기 노선기존 개념 “반복과 분기”, “규칙과 논리 추론”에 재시도와 제약 조건을 연결할 수 있습니다.새 개념을 만들기 전에 기존 정의와 대조합니다. “데이터를 안전하게 남기려면?” 노선은 알고리즘의 단계 세기 → Prisma의 모델링 → 중복·실패 실험 순서로 계획합니다.

반대 의견과 결론

민재 관점의 반대 의견은 “일반 SQL 책에 Prisma 한 장만 넣으면 충분하지 않은가?”입니다. 알고리즘 책은 탐색과 자료구조를, AI 인프라 책은 모델 서버와 운영을 주로 다루므로 스키마·Client·마이그레이션을 같은 사례로 연결하는 범위가 비어 있습니다. 별도 한 권을 만들되 알고리즘의 시간 복잡도나 서비스 배포 원리를 다시 길게 쓰지 않고 기존 책으로 보냅니다. ORM이 SQL이나 데이터베이스 이해를 대체한다는 인상을 주면 이 기획의 목적을 벗어납니다.

구현 전에 정한 변경·확인 범위

신규 파일은 books/prisma/의 본문·실험·그림·테스트·문서입니다. 통합 단계에서 카탈로그, 서가 생성 결과, 작업 상태, 필요한 기존 책의 연결 문구와 CI 테스트 목록을 수정합니다. 학습자는 설치 없이 개념 실험을 조작하고, 별도의 로컬 코드 실습으로 실제 Prisma 동작을 확인하게 됩니다. 브라우저 시뮬레이션이 실제 Prisma 엔진 실행인 것처럼 표시하지 않습니다.

검증 계획은 모델 계산의 정상값·경계값·불변 조건, 10개 장과 복습 문제의 경로, 1280·390·320px의 조작·초기화·키보드·서가 복귀, 실제 설치 예제의 수행 여부, 새 세션의 출처·팩트 검수입니다. 수행하지 못한 항목은 실행 성공으로 기록하지 않습니다.

범위와 깊이

구분내용깊이를 정한 이유
핵심관계형 DB 최소 개념, schema, 생성·설정, CRUD, 관계 조회, 변경 이력, 트랜잭션·멱등성, 테스트·권한저장소를 설계하고 수정한 코드가 실제 데이터를 다룰 때 반드시 연결해야 하는 범위입니다.
선택 심화관찰한 SQL 읽기, 인덱스 선택의 조건, offset/cursor 페이지 방식, PostgreSQL과 SQLite 차이, 기존 DB introspection처음 읽을 때는 핵심 설명 뒤에 두고, 일반적인 성능 보장이나 DB 간 완전 호환을 주장하지 않습니다.
별도 학습SQL 전체 문법, 고급 정규화 이론, DB 내부 구현, ORM 간 벤치마크, MongoDB, Prisma 유료 서비스 상세, 프레임워크별 인증·배포, Prisma 8 전환 실습이 책의 마지막 과제에 필요하지 않거나 버전·서비스별 변동과 별도 검증 부담이 큽니다.

범위 비교의 기준 자료는 Prisma ORM 7 공식 문서의 Client·Schema·Migrate 분류입니다. 구체적인 원문 URL, 확인일, 확인되지 않은 부분은 조사 노트에서 확정합니다. 이 기획 단계에서 외부 강의 계획서 여러 편을 비교했다고 주장하지 않습니다.

마지막 과제 초안

프로젝트 A에 속한 작업 T를 실행하면서 요청 키 R을 저장합니다. 첫 응답을 받지 못해 R을 다시 제출했고, 별도 테스트에서는 실행 기록 생성 직후 의도적으로 실패시킵니다. 이어 프로젝트 B의 사용자 문맥으로 T의 상태를 바꾸는 요청을 보냅니다. 독자는 중복 생성·부분 반영·프로젝트 경계 위반을 각각 막는 조건을 고르고, 한 장짜리 설계 기록에 스키마 제약, 읽기·쓰기 조건, 트랜잭션 범위, 실패 테스트와 배포 순서를 적습니다. 외부 API 호출까지 DB 트랜잭션으로 되돌릴 수 있다는 답은 오답입니다.

3. 장 학습 설계 · G3 교수법 산출물

아래 표는 실제 실험 구현 전에 정한 학습 설계입니다. 조사 노트와 구현이 준비되면 변수명·기본값·관찰 결과를 본문과 대조합니다. G3의 조사·교수법 검토를 마쳤으며, 원고와 실험의 구현 완료를 뜻하지 않습니다. 모든 실험은 입력을 바꾸기 전에 예측을 남기게 하고, 정해진 시나리오와 실제 계산 및 실제 Prisma 실행을 구분합니다.

장도달 목표·회상문제·예측조작·관찰설명·전이확인 의도·수준
