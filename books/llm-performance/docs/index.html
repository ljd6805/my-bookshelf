지안의 판정: 목표 행동은 “두 부하 조건에서 평균과 p95가 늘어난 양을 비교하고, ρ ≥ 1이면 숫자 대신 불안정이라고 보고한다”입니다. 여섯 단계가 모두 있고 직접 해 보는 단계가 있어 멈출 사유는 없습니다. 다만 tail 전용 전이 문항이 없고, 깊이 읽기와 “결과 읽기”가 예측 질문 바로 뒤에 답을 보여 줘 예측의 힘이 약합니다. “결과 읽기”가 먼저 보이는 것은 책 전체 실험 안내의 공통 형식이라 이번 범위에서 바꾸지 않고 남은 일로 둡니다.

10 · 빈자리에 다음 요청 넣기 — 깊이 읽기 “부하가 오르면 꼬리가 먼저 무너진다”와 실험 문장

인용진단고친 문장 / 판단
“1초에 도착하는 일(λ × S)이 슬롯 4개가 1초에 끝내는 일보다 많습니다”다온: 단위가 맞지 않아 걸립니다(λ × S는 개수).“들어오는 일의 양 λ × S는 슬롯 몇 개가 쉬지 않고 일해야 따라잡는지를 뜻하는데, 슬롯은 4개뿐입니다.”(집필 중 반영)
“꼬리가 평균보다 훨씬 빨리 커진다”다온: 비율로 읽으면 틀립니다. p95/평균 비는 오히려 줄어듭니다.늘어난 ms를 직접 비교하는 문장으로 바꿈(집필 중 반영)
“요청 대부분은 여전히 금방 슬롯을 얻지만”다온(검수 회차): ρ 0.9에서는 79%가 기다리므로 근거 없는 일반화입니다.“ρ 0.5에서는 요청의 85%가 기다리지 않고 ρ 0.9에서도 절반은 0.7초 안에 슬롯을 얻지만…”(검수 때 반영)
“처리량과 지연을 따로 재야 하는 이유가 하나 더 생긴 셈입니다.”다온: 맺음 상투구에 가깝습니다. 나래: 앞 문장(S가 함께 커진다)의 결론을 장의 주제인 처리량·지연 구분으로 되돌려 주는 문장이라 흐름상 필요합니다.유지
“첫 번째 실험의 네 요청은 처음부터 모두 줄 서 있었습니다.”나래: 앞 실험의 결과를 쥐고 새 질문으로 넘어가는 다리 문장입니다. 장 머리와 마지막 문단(11장으로 가는 통신 비용 문장)은 바뀌지 않았습니다.유지
첫 문단 “λ는 …, S는 …, c는 … 슬롯 수입니다.”나래: 한 문단에 기호 넷(ρ·λ·S·c)이 한꺼번에 나옵니다. 바로 뒤에 숫자 예(초당 2개 → 0.5)가 붙어 읽히지만 무겁습니다.이번에는 유지. 다음 개정에서 기호를 실험 라벨과 같은 말(도착률·처리 시간·슬롯)로 먼저 부르는 방안을 남김

나래의 확인: 번역투·뜻 없는 도입·과장 표현은 찾지 못했습니다. 용어는 “사용률 ρ”, “리틀의 법칙”, “p95 대기”로 실험 라벨·결과 문장·본문에서 같은 이름을 씁니다. 공통 사례(회의록 요약)를 이 문단에서 직접 부르지 않는 점은 해원의 G2 메모와 같은 제안으로 남깁니다.

2026-10-12, Chromium(Playwright)으로 http://127.0.0.1:8794/books/llm-performance/#batching을 처음 읽는 독자처럼 1280·390·320px에서 따라갔습니다. 책 브라우저 검사 tests/browser.cjs도 같은 서버에서 다시 돌려 47화면·45실험 통과, 콘솔 오류 0이었습니다(결과는 저장소 밖에 저장).

  • 예측: 깊이 읽기 둘째 문단과 실험 끝 “직접 해 보기”가 같은 질문(평균과 p95 중 어느 쪽이 더 늘까)을 냅니다. 첫 독자는 “둘 다 비슷하게 늘 것”이라고 답하기 쉽습니다. 다만 같은 문단과 실험 안내의 “결과 읽기”가 답(963 ms, 2,776 ms)을 바로 보여 주므로, 누르기 전에 예측을 적게 하는 힘이 약합니다(남은 일).
  • 조작: 예제 ρ 0.5를 누르면 ρ 0.50·안정, 평균 47·p95 364 ms, 기다린 요청 15.3%, TTFT p95 464 ms. ρ 0.9를 누르면 평균 963·p95 2,776 ms와 “평균 916 ms, p95 2,412 ms 늘어 꼬리가 2.6배 많이 늘었다”는 문장이 나옵니다. 지수 흔들림은 p95 7,108 ms, ρ 1.05는 “불안정”과 처음 1/4 9.8 s → 마지막 1/4 44.9 s 막대로 바뀝니다. 초기화 후 λ 2·S 1000·c 4·균등으로 돌아오고, 도착률 슬라이더는 방향키 다섯 번에 2 → 2.5로 움직입니다.
  • 관찰: 상태는 색만이 아니라 “안정/불안정” 글자, 평균 실선과 p95 점선, 막대마다 aria-label 숫자로 읽힙니다. ρ 0.5에서는 기다리지 않은 요청 막대가 커서 꼬리 막대가 잘 보이지 않습니다(검수 제안과 같음).
  • 설명: 결과 문장이 늘어난 ms 두 개와 배수, 리틀의 법칙 검산(3.481개 = 3.617/s × 0.963 s)을 함께 주므로 독자는 “평균만 보면 꼬리가 늦게 보인다”와 “ρ ≥ 1이면 숫자를 보고하지 않는다”를 자기 말로 설명할 수 있습니다.
  • 리안의 실험 점검: 실험 블록은 책의 형식(EXPERIMENT 번호·제목·설명·무엇을 확인하나요·예제 네 개·초기화·결과 읽기·조작부·결과·직접 해 보기)을 따릅니다. 계산은 PMath.queue·histogram·tailSweep(js/math.js), 렌더링은 L.tail(js/labs-serving.js)로 나뉘고 함수는 모두 100줄 이내입니다. 입력 네 개에 라벨이 있고 id 중복이 없으며(검수 때 slots → servers), 320px에서 가로 넘침 0px입니다. 오류 상태는 입력 범위를 슬라이더가 막고, 의미 있는 경계인 ρ ≥ 1을 글자로 알립니다. 그림은 “대기 ms별 요청 수 · 첫 막대는 기다리지 않은 요청”이라는 한 문장 설명을 답니다. 320px에서 SVG 글자가 작아지는 점은 책 공통 SVG 방식이라 그대로 둡니다.
  • 남은 일: tail 전용 전이 문항, 예측 전에 답이 보이는 안내 형식, 장 시간 표기, 실제 독자 확인(L4).
